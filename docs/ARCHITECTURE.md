# 構成案と権限境界

## 1. 推奨構成

```text
承認済みスマホ
  → 私設ネットワークの端末・利用者制限
  → HTTPS入口（アプリ認証も必要）
  → ローカル中継（外部へ直接公開しない）
      ├─ 会話アダプター → 正規の既存バックエンド
      ├─ 成果物アダプター → 会話に紐づく専用成果物領域だけ
      └─ 監視アダプター → 登録済みワーカーの固定読み取り機能だけ
```

中継、正規バックエンド、ワーカー監視を別の責任にする。アプリからバックエンド秘密をブラウザへ渡さない。一般公開するWebサイトやGitHub Pagesを接続入口にしない。

## 2. ネットワーク方式を選ぶ

| 案 | 採用判断 | 注意点 |
|---|---|---|
| 私設ネットワークHTTPS入口 + loopback中継 | 推奨。HTTPSとネットワーク制限を両立しやすい | 入口のアクセス規則、元ポートの非公開性、転送ヘッダーの信頼境界を確認 |
| 私設ネットワークIPに限定した直接待受 | HTTPS入口を用意できない場合の別案 | そのIPだけにbindし、外部経路・LAN経路も検査。CookieのSecure要件を満たすTLSを別途用意 |
| 公開トンネル、ポート転送、一般公開URL | 本下書きでは不採用 | インターネット公開サービスとして別の脅威モデル・運用体制が必要 |

Tailscaleの場合、Serveはtailnet内の共有、Funnelはインターネット公開です。[2][3] 「Tailscaleを入れた」だけで承認済み端末だけに限定できたと判断しない。

プロキシ利用時は、アプリに届く送信元がloopbackでも外側の認証を省略しない。HostとOriginは、利用者が承認したHTTPS入口との一致を確認する。Forwardedヘッダーは決めたプロキシから来たものだけ扱い、無条件で信用しない。

## 3. ファイル領域の分離

- `PUBLIC_ASSETS`：静的UIだけ。状態ファイル、会話、設定を置かない。
- `STATE_DIR`：認証・端末・タスク等の私有状態。HTTP配信対象外。ソースツリーの外に置く。
- `ARTIFACT_ROOTS`：利用者が個別承認した成果物専用領域。ホーム、ドライブ根、プロジェクト全体を既定にしない。
- `SECRET_STORE`：OSの資格情報保管または厳しいACL付きの非公開領域。コードは秘密値ではなく参照名を使う。
- `BACKEND_WORKSPACE`：エージェントが触れる領域。HTTP配信領域とは別の権限問題として制限する。

OSのドライブ文字を消すのはプライバシー対策であり、アクセス制御ではない。実際の読み取りを止めるのは認証、領域の許可リスト、OS権限、必要ならサンドボックスである。

**特に重要：会話の送信権限は、エージェントのツール実行権限に繋がり得る。** 配信を狭くしても、エージェント自身が広いファイル読取権限を持てば、プロンプトでその内容を要求できる。私有領域を絶対に読ませたくない場合は、別OSユーザー・コンテナ等と承認制ツールで境界を作り、その境界を実試験する。

## 4. アダプターの能力契約

| 一般機能 | 実装側が確認すること | 不明・未対応の場合 |
|---|---|---|
| 正規会話の一覧と履歴 | 保存ID、プロフィール、読み取り認可 | 閲覧失敗を表示。別会話へ自動切替しない |
| live会話に共有接続 | 保存IDと実行IDとowner世代 | 未確認なら送信禁止 |
| 保存会話の再開 | 履歴のみ再開、勝手に推論継続しない | 閲覧専用を維持 |
| 使用中会話の引き継ぎ | 対象runtimeの正規終了、解放読み戻し、同保存ID再開 | UIで理由表示。kill・ロック削除で代用しない |
| モデル選択 | 会話scope、設定済み候補、追加コスト警告 | 既定モデル・別会話を変更しない |
| 遠隔GPU監視 | 許可済みhostの固定読み取り、nullと実測の区別 | 未対応・取得失敗・古い値を区別 |

Hermesでは導入版の公式資料と実応答を確認する。[1] 保存IDと実行ID、再開ACKと排他の確保、バックエンドHTTPとイベント方式を同一視しない。非公開の内部APIが必要なら互換性条件を明記し、汎用対応を保証しない。

## 5. 秘密をLLMへ渡さない設定フロー

LLMにはOS種別、必要機能、単一/複数マシン、認証方式の選択だけ渡す。実パス・URL・host・鍵は利用者がローカル設定画面で入力し、クラウドLLMを経由させない。中継は実行時に必要な値を読めるが、画面、ログ、診断出力へ戻さない。

LLMがツール実行を通して値を収集すれば、プロンプトに手入力していなくても送信される可能性がある。生成中は既存秘密ファイルの探索禁止、環境変数の一括表示禁止、全設定のダンプ禁止とし、秘密を扱う初期設定はLLMセッション外で行う。

この境界は構築時の設定秘密を扱うもの。日常の会話・添付に秘密を含めれば、推論先へ渡り得る。会話内容を外部へ送らないという別要件がある場合は、推論経路とツールをローカルに限定し、その挙動を別に検証する。匿名化した診断の設計だけで「秘密が絶対に出ない」と保証しない。

## 6. OSと運用能力の差

秘密保管はOSの資格情報機能をアダプター化する。Windows向け暗号化・ACLの実装をLinux/macOSへそのまま移植したことにしない。保管機能が無い場合は制限付きの私有設定か別の秘密保管を利用者に選んでもらい、平文保存へ黙って縮退しない。

GPU監視は任意機能。対応する収集器が無ければ未対応を表示する。遠隔専用APIを置く案もあるが、認証・TLS・登録済み相手・固定レスポンス・許可されたネットワークだけの条件はSSH案と同じ。APIを置くためのワーカー変更・依存追加は承認対象。

healthは生存の最小情報だけとし、ownerのPID、起動時刻、内部接続先、会話数等の診断は認証付きにする。起動監視のために実環境の構成を匿名入口へ返さない。
